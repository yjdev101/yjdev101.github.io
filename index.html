남의 채팅방을 엿보거나 가짜 메시지를 넣을 수 있던 구멍

commit 7e6aefbStompAuthInterceptor보안

문제
/sub/chat/*을 구독하면 모든 채팅방 대화를 받을 수 있었고, /sub/chat/5로 직접 보내면 검사 없이 남의 방에 메시지가 뿌려졌습니다.
원인
구독 검사가 채팅방 주소 모양(/sub/chat/숫자)만 확인하고 다른 모양은 통과시켰습니다. 그런데 메시지 브로커는 *를 "모든 방"으로 해석했습니다. 전송은 아예 검사하지 않았습니다.
해결
허용 목록 방식으로 바꿨습니다. 구독은 참여한 채팅방과 개인 에러 큐만, 전송은 컨트롤러로 가는 /pub/ 주소만 허용합니다. /pub/으로 들어온 메시지는 서비스에서 참여자인지 한 번 더 확인합니다.

'채팅하기'를 두 번 누르면 500 에러

commit 7e6aefbChatService.openChatRoom트랜잭션 · 동시성

문제
같은 사람이 같은 상품에 버튼을 동시에 두 번 누르면, 방은 하나만 생기는데 두 번째 요청은 서버 오류를 받았습니다.
원인
두 요청이 모두 "방 없음"을 보고 만들려 해서 UNIQUE 제약에 걸렸습니다. 예외를 잡아 기존 방을 돌려주려 했지만, 트랜잭션에 이미 롤백 표시가 붙어 커밋 시점에 실패했습니다.
해결
예외를 잡는 대신 예외가 아예 나지 않게 했습니다. 두 요청 모두 같은 방을 돌려받습니다. 
INSERT INTO chat_room (item_id, buyer_id, seller_id)
VALUES (:itemId, :buyerId, :sellerId)
ON CONFLICT (item_id, buyer_id) DO NOTHING

'거래 완료'와 '취소'가 동시에 들어오면

commit 7e6aefbTransactionService.changeStatus비관적 락

문제
판매자의 완료와 구매자의 취소가 동시에 오면 둘 다 통과할 수 있었습니다. 최악의 경우 거래는 완료인데 상품이 다시 판매 중으로 올라갑니다.
원인
락은 있었지만 순서가 틀렸습니다. 거래 상태를 먼저 검사하고 상품을 나중에 잠가서, 두 요청이 모두 잠그기 전의 상태를 봤습니다.
해결
거래 row를 먼저 잠그고 나서 상태를 검사하도록 순서를 바꿨습니다. 두 번째 요청은 기다렸다가 바뀐 상태를 보고 거절됩니다. 
SELECT t FROM Transaction t WHERE t.id = :id   -- @Lock(PESSIMISTIC_WRITE) → FOR UPDATE
